The problem with how agents pay today

Every agent payment method today is a leak waiting to happen — on every chain

A shared API key. A linked corporate card. A hot wallet with a public address. Every funding source available to an autonomous agent right now is static, reusable, and fully linkable — which means one look at that source exposes an agent's entire vendor list, spend cadence, and purchasing pattern, forever. This isn't a Starknet problem or an Ethereum problem. It's structural to how agents transact anywhere, regardless of chain.

Competitive exposure

Watch a funding address for a day and you know exactly which data vendors, model providers, and compute markets an agent fleet depends on.

Price discrimination

A service that recognizes a repeat-paying address can quote it differently than an unknown one — silently, with no way to tell.

Blast radius

One exposed key or card number doesn't cost one purchase. It costs the entire transaction history behind it.

No attribution control

Today's options are binary: a fully public wallet, or a card that hides everything — including from your own audit trail. Nothing lets you choose per purchase, on any chain.

The fix

One infrastructure layer.
Native privacy, per chain.

Shield funds once. From there, every purchase gets its own credential — capped to one amount, one endpoint, one expiry window, redeemable exactly once. Choose, per action, whether that purchase settles privately or publicly. This pattern doesn't change chain to chain. What changes is how it's realized underneath: OXA builds on whatever native privacy primitive a given chain actually offers, rather than forcing one cryptographic model onto every ecosystem it touches. Today, that means Starknet's STRK20 shielded-pool architecture, live and real.

The flow, live today (Starknet)

Four steps. Every one of them a real on-chain transaction.

01

Shield

Connect your existing Starknet wallet and shield funds into the pool. No new wallet, no new custody model.

02

Set policy

Define spend caps, endpoint allowlists, and privacy defaults per category. Lock a category to private-only if it should never be public.

03

Request

Mid-task, an agent asks for a scoped credential — one endpoint, one amount, one TTL. Policy is checked before anything moves.

04

Redeem

The endpoint redeems the credential directly, once. Funds land. Replay is structurally impossible, not just discouraged.

What every credential guarantees

Single-use

A redeemed credential cannot be redeemed again — enforced on-chain, not by convention.

Endpoint-scoped

A credential is only valid for the one service it was issued to.

Time-bound

Every credential expires. Unused funds return to the owner, not to limbo.

Mode-per-action

Private or public is chosen per purchase, not once for the whole account.

Non-custodial funding

The owner's shielded balance stays theirs, on every chain — issuing never requires keys.

On-chain enforced policy

Spend caps and endpoint allowlists are checked in the contract itself.

These are OXA's invariants as a protocol. How each one is technically enforced depends on the chain underneath — see Security Model for the Starknet-specific implementation.

How it's actually built

One pattern. Chain-native cryptography underneath.

OXA's architecture separates a chain-agnostic pattern — shield once, issue scoped one-time credentials, redeem once, reclaim if unused — from the chain-specific primitives that make each step real. On Starknet, that means composing STRK20's own already-live infrastructure:

  • Owner Wallet — existing account, holds viewing key
  • Policy Registry — on-chain contract for caps/allowlists
  • Credential Issuer — anonymizer satisfying privacy_invoke
  • Broker — service agent talks to, resolves policy
  • Endpoint — crypto-native redeeming service

What's actually enforced, per chain

Every claim here is checkable on-chain. Nothing hand-waved.

  • Domain-separated commitments binding a credential's secret and its endpoint together.
  • On-chain policy re-check at mint time, not trusted from an off-chain service alone.
  • Checks-effects-interactions ordering on every state-changing call.
  • Threat model published, not implied — every identified risk, including ones not yet fully closed, documented in the open.

This pattern follows STRK20's own unaudited anonymizer reference. Treat this as a working proof of the mechanism, not a production-hardened system, until a formal audit says otherwise. Each future chain implementation will carry its own, separately-stated security model — security properties from one chain's primitive don't transfer to another's by assumption.
